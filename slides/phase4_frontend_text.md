### 実測①：ブラウザは API を一度も叩いていない（→ S6 に反映したい）

ホーム画面を開いた状態で計測した結果。

```

画面に表示されているデータ   : 集計・カテゴリ別・支払い手段別・支出10件
```

`curl http://localhost:3000` でサーバーが返す HTML を見ると、既に数字が入っている。

```
「¥ 22,868」（合計）      → HTML に含まれる
「中華食材」（支出のメモ） → HTML に含まれる
```

つまり **ブラウザが JavaScript を動かす前から、データは画面に載っている**。
これが S4「サーバーコンポーネントはブラウザに JS を送らない」の実物。

### 実測④：React 19 はフォームを毎回自動リセットする（→ S9 に反映したい）

実装して初めて分かった挙動。

### 実測⑥：月の切り替えは URL に持たせればサーバーのままでいられる（→ S5 / S6 に反映したい）

月次清算画面の「◂ 前の月 / 次の月 ▸」の実装で判断したこと。

```
useState で月を持つ場合:
  → MonthNav がクライアントコンポーネントになる
  → 月が変わったら集計を取り直すため useEffect + fetch が必要
  → ローディング状態の管理も自前でやることになる

<Link href="/settlement/2026-06"> の場合:
  → URL が変わってページ全体がサーバーで再描画される
  → MonthNav はサーバーコンポーネントのまま
  → 集計はサーバーで取得済みの状態で届く
```

「月を選ぶ」は一見すると状態管理に見えるが、**URL に持たせればサーバーのままでいられる**。
S5「'use client' は葉に付ける」の応用例として使える。

実装した月次清算画面のクライアントコンポーネントは**ボタン1つだけ**（`SettlementActionButton`）。
集計表示・月ナビ・過去履歴はすべてサーバーコンポーネント。

### 実測⑦：フィルタを URL に持たせるとサーバーで絞り込める（→ S5 / S6 の決定打）

支出一覧の絞り込み（月 / カテゴリ / 支払い手段 / 支払者）を **URL のクエリパラメータ**で
表現した。`useState` は使っていない。

`curl` でサーバーが返す HTML を取ると、**件数と合計が既に絞り込まれている**。

| URL | サーバーが返した HTML の中身 |
| :---- | :---- |
| `/` | 11 件 / ¥25,468 |
| `/?category=1`（食費） | **5 件 / ¥13,134** |
| `/?method=cash`（現金） | **4 件 / ¥10,994** |
| `/?payer=2`（ひつじ） | **4 件 / ¥8,248** |
| `/?category=1&method=cash` | **3 件 / ¥8,414** |

ブラウザで JavaScript が動く前に、もう絞り込みが終わっている。

**もし `useState` で絞り込んでいたら**：
- そのコンポーネントがクライアント化する
- 条件が変わるたびに `useEffect` + `fetch` で取り直す必要がある
- ローディング状態も自前で管理する
- 絞り込んだ状態を共有・ブックマークできない

URL に持たせたことで、一覧テーブルは**サーバーコンポーネントのまま**でいられた。
クライアントなのは絞り込みの `<select>` と、行内編集・削除のボタンだけ。

### 実測⑧：ナビも「現在地の判定」だけがクライアント（→ S5 の補強）

3画面を行き来するナビを実装したときの判断。

「今どの画面にいるか」で見た目を変えるには `usePathname` が要る。
これはブラウザ側でしか分からないので `'use client'` が必要になる。

ただしクライアントにしたのは**ナビ本体だけ**：

```
app/layout.tsx              → サーバーのまま（ナビを置くだけ）
AppNavSection.tsx           → サーバー（未判定件数を API から取る）
  └─ AppNav.tsx             → ★クライアント★（usePathname で現在地判定）
```

未判定バッジの件数は `AppNavSection`（サーバー）が取って props で渡している。
ナビ自身は API を叩かない。

`layout.tsx` にクライアントを置いても、**配下のページはサーバーのまま**でいられる。
「'use client' は伝播するが、それは *子* に対してであって、
兄弟や親には及ばない」という点が実装して腑に落ちた。

### 実測⑨：Server Actions を選んだら LAN 公開が起動オプション1つで済む

（発表で触れるかは任意）

```
クライアントから直接 API を叩く設計だった場合:
  スマホのブラウザ → http://127.0.0.1:8000 を叩こうとして失敗
  → バックエンドを 0.0.0.0 で公開 + CORS 設定 + URL 書き換えが必要

Server Actions の場合:
  スマホのブラウザ → Next.js(3000) だけを叩く
  → Next.js が 127.0.0.1:8000 を呼ぶ（PC内部なのでそのまま動く）
  → バックエンドは無変更。CORS も不要
```

`npm run dev -- -H 0.0.0.0` だけで同じ Wi-Fi のスマホから開ける。

## S5 境界：どう対応するか

**ラベル**：境界 ｜ サーバーとクライアント
**タイトル**：どう対応するか：判断は1問だけ

### ブラウザでしか出来ないことを使うか？

**「ブラウザでしか出来ないこと」とは**

- `onClick` / `onChange` / `onSubmit`（操作への反応）
- `useState` / `useReducer`（状態を持つ）
- `useEffect`（副作用）
- `localStorage` / `window` / `document`

| 答え | どうする |
| :---- | :---- |
| Yes | クライアント（`'use client'` を書く） |
| No | サーバー（既定。何も書かない） |

**原則：`'use client'` は葉に付ける。根に付けない**
ページ（根）に `'use client'` を書くと配下が全部クライアントになる。
ただし layout の中にクライアント部品を「置く」のは別。その部品だけがクライアントで、children はサーバーのまま。

**今日の一手**：最初に作る画面で、クライアントが必要な部品を1つだけ決める

**結論**：既定はサーバー。操作がある部品だけをクライアントに切り出す。

> **ノート**：判断基準を1問に絞るのがポイント。

## S8 接続：どう対応するか

**ラベル**：接続 ｜ データの取得と更新
**タイトル**：どう対応するか：取得と更新で経路を分ける

| 操作 | 経路 | 書き方 |
| :---- | :---- | :---- |
| 表示（GET） | サーバーコンポーネント | `async function` にして直接 `await` する |
| 変更（POST / PATCH / DELETE） | Server Actions | `'use server'` を書き、最後に `refresh()` を呼ぶ |

```
表示：サーバーコンポーネント

export default async function Page() {
  const data = await apiGet('/api/expenses/')
  return <ExpenseList items={data.items} />
}
```

```
変更：Server Actions

'use server'
export async function createExpense(fd) {
  await fetch(API + '/api/expenses/', {...})
  refresh()
}
```

### 実際に支出を1件登録したときの変化（ページ遷移なし）

| | 合計 | 件数 | 外食カテゴリ | 送金額 | ブラウザのAPI呼び出し |
| :---- | :---- | :---- | :---- | :---- | :---- |
| 送信前 | ¥20,288 | 9 件 | ¥2,800（1件） | ¥1,896 | 0 |
| 送信後 | **¥22,868** | **10 件** | **¥5,380（2件）** | **¥3,186** | **0** |

集計・グラフ・一覧が同時に更新される。個別に取り直すコードは書いていない（`refresh()` 1行だけ）。

**結論**：表示はサーバーで `await`、変更は Server Actions。更新後は `refresh()`。

> **ノート**：経路を分けるのが結論。Server Actions は Phase 5 の認証にも効く。Server Actions を選んだ理由: API の URL がブラウザに出ない / CORS 設定が不要 / Phase 5 で Cookie を扱うとき有利。

## S9 接続：対応の実例 ★山場★

**ラベル**：接続 ｜ データの取得と更新
**タイトル**：対応の実例：調べたら記事と違っていた

**条件**：検索で出てきた記事を見ながら書こうとした。書き方が記事どうしで食い違っていた。

| 項目 | 記事に多い情報（13〜14） | 実際（16.3.1） |
| :---- | :---- | :---- |
| fetch のキャッシュ | 既定でキャッシュされる | **キャッシュされない** |
| キャッシュ回避 | `{ cache: 'no-store' }` を明示 | **不要（既定がその動き）** |
| 更新後の画面反映 | `router.refresh()` をクライアントで | **`refresh()` を Server Action 内で** |
| 変更処理 | クライアントから `fetch(POST)` | **Server Actions** |

### しかも、Next.js 自身が警告していた

― `npm run dev` が `AGENTS.md` を自動生成する

```

This version has breaking changes — APIs,

differ from your training data. Read the

docs/ before writing any code.
```

**読み取れること**

- フレームワーク自身がバージョン差の問題を認めている
- ドキュメントが `node_modules` に同梱されている

## S11 画面：どう対応するか

**ラベル**：画面 ｜ 作る範囲を決める
**タイトル**：どう対応するか：使用頻度で切る

画面を1つずつ、この3問にかける。No が多いほど独立させる必要がない。

1. その画面を週1回以上使うか
2. 他の画面に入れられないか
3. その画面が無いと運用が止まるか

| No の数 | やること |
| :---- | :---- |
| 0 | そのまま作る |
| 1〜2 | 他の画面に統合する |
| 3 | 作らない（API は残す） |

**大事な点：機能を消すのではなく、画面を作らない**

**結論**：使用頻度が低い画面は独立させない。API は残して UI だけ作らない。

> **ノート**：YAGNI の実践。判断を3問に落とす。

## S12 画面：対応の実例

**ラベル**：画面 ｜ 作る範囲を決める
**タイトル**：対応の実例：7画面 → 3画面

| 当初の画面 | 判断 |
| :---- | :---- |
| ダッシュボード | 残す（ホームに改称） |
| 支出一覧 | **ホームに統合** |
| 月次清算 | 残す |
| PayPay 取り込み | 残す |
| カテゴリ管理 | **廃止** |
| ログイン | Phase 5 に送る |
| アカウントメニュー | **廃止** |

**廃止した機能の行き先**

- 支出一覧 → ホーム下部に統合。編集は行内で
- カテゴリ追加 → 入力欄の「+ 新規」
- 並び替え・アーカイブ → 作らない
- 表示名・パスワード変更 → Phase 5

**得たもの**：実装が概ね半分になり、Phase 5 に早く進める。

**代償**

- カテゴリの並び替えが UI からできない（API は残してある）
- モックを作り直す手間が発生した（PC 版とスマホ版で6枚）

**結論**：使用頻度で切る。API を残しておけば、後から画面を足せる。

> **ノート**：モックの作り直しは代償として正直に話す。ただ実装前に気づけたので手戻りは小さかった。
